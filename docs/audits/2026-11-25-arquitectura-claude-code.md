# Arquitectura de Claude Code en Sityos

**25 de noviembre de 2026 · Revisión del checkout `develop`, commit `b07cac1`.**

**Sí conviene un `CLAUDE.md` propio en la raíz de `sityos-agents`.** Su cometido es explicar cómo mantener y probar el marketplace y sus componentes. Cada proyecto consumidor debe declarar su stack real, sus herramientas y su política de ejecución. El global debe conservar preferencias personales de aplicación general. La mayor debilidad del sistema actual está en el ciclo CEO: la versión que carga Claude puede diferir de la revisada, y los límites de ejecución, el aislamiento de los trabajos y la evidencia de despliegue dependen en parte de instrucciones que el modelo interpreta. La prioridad es hacer verificables esos contratos y pilotarlos en un único proyecto antes de ampliar el despliegue.

## 1. Las instrucciones de cada proyecto necesitan una fuente propia

**La raíz del marketplace carece de `CLAUDE.md` y `AGENTS.md` versionados.** El global activo es un enlace a `global/CLAUDE.md`, de 275 líneas. Mezcla preferencias, inventario de proyectos, marca, arquitectura, catálogo de skills, normas de varios lenguajes y el procedimiento CEO. La sección de convenciones pide que cada proyecto mantenga un `AGENTS.md` canónico importado por Claude. Los `CLAUDE.md` se agregan al contexto y las contradicciones entre ellos quedan sujetas a interpretación. Anthropic recomienda menos de 200 líneas por archivo, y extraer un texto mediante `@archivo` conserva su coste de contexto. [Global del repositorio](../../global/CLAUDE.md:26) · [Criterios de Anthropic](https://code.claude.com/docs/en/memory#write-effective-instructions) · [Carga de instrucciones](https://code.claude.com/docs/en/memory#how-claude-md-files-load).

Recomiendo un `AGENTS.md` de raíz con las convenciones compartidas por Claude Code y Codex, la responsabilidad de cada componente y los comandos de comprobación. El `CLAUDE.md` importa `@AGENTS.md` y añade cómo cargar el plugin local, comprobar qué versión se ejecuta y probar los puntos de entrada de Claude Code. Las reglas para manifiestos, hooks o prompts pueden crecer en `.claude/rules/` con `paths` específicos. Ajustar primero el `.gitignore`: hoy excluye `/.claude/` por completo, así que deben definirse exclusiones precisas para configuración personal y worktrees cuando se empiece a versionar contenido compartido. [Gitignore](../../.gitignore:4) · [Reglas por ruta](https://code.claude.com/docs/en/memory#path-specific-rules).

En la versión observada, **Claude Code 2.1.332**, `AGENTS.md` ya se descubre directamente cuando no hay `CLAUDE.md` o `CLAUDE.local.md` de proyecto en la ruta y se usa la configuración predeterminada. El global del usuario no impide ese descubrimiento. El import explícito sigue siendo útil donde se añade un `CLAUDE.md` local y para sesiones con soporte distinto. En la muestra, AI-Automation y finanzas-mcp ya usan el puente corto. crypto-trading y viral-videos-platform tienen instrucciones largas duplicadas entre ambos archivos. Consolidarlas por proyecto reduce las discrepancias y facilita revisar cambios. [Lectura de AGENTS.md](https://code.claude.com/docs/en/memory#agentsmd) · [AI-Automation](../../../AI-Automation/CLAUDE.md) · [finanzas-mcp](../../../finanzas-mcp/CLAUDE.md) · [crypto-trading](../../../crypto-trading/CLAUDE.md) · [viral-videos-platform](../../../viral-videos-platform/CLAUDE.md).

**`project-override/` es una plantilla específica de Drupal con datos desactualizados.** Incluye DDEV y `web/`, y documenta una rama de producción distinta de la configurada en AI-Automation, que trabaja con `docroot/` y Make sobre Compose, usa `develop` para PR y despliega desde `master`. Tampoco importa `AGENTS.md`. Su instalación genérica en cualquier carpeta puede inducir comandos y rutas incorrectos. Sustituiría la copia por una plantilla mínima que se complete con comprobaciones reales en cada repositorio. El proyecto debe poseer sus comandos de validación, configuración de despliegue e instrucciones de entorno. ## 2. El marketplace puede distribuir capacidades sin configurar toda la máquina

| Pieza | Ubicación y contrato propuestos |
| --- | --- |
| Instrucciones globales | Preferencias personales estables como idioma, estilo y convenciones comunes. El inventario y la marca viven en documentación de consulta. |
| Instrucciones de proyecto | `AGENTS.md` canónico, `CLAUDE.md` breve con import y reglas por ruta. Cada repositorio documenta sus comandos y sus decisiones. |
| Skill | Procedimiento reutilizable o conocimiento especializado. Descripción precisa con condiciones de uso, cuerpo corto y referencias o scripts a demanda. |
| Comando de usuario | Punto de entrada estable para una operación. Nueva implementación en `skills/<nombre>/SKILL.md`. Operaciones con efectos declaradas con `disable-model-invocation: true`. |
| Subagente | Contexto de ejecución separado con objetivo, entrada, resultado, modelo y conjunto mínimo de herramientas. Las adaptaciones de stack permanecen en el proyecto. |
| Plugin | Unidad de distribución y versión. Mantener `ceo-system` separado de las skills de desarrollo. Si se reutilizan en varios proyectos, empezar con un único paquete opcional de skills Sityos y dividirlo cuando haya necesidades distintas de instalación o actualización. |
| MCP y permisos | Configuración explícita de proyecto o local. Las identidades, secretos y herramientas disponibles siguen la necesidad del consumidor. |

Los cuatro directorios `agents/sityos-*/SKILL.md` son **skills** y se enlazan en `~/.claude/skills`. Los tres agentes reales del marketplace están en `plugins/ceo-system/agents/`. La ubicación actual confunde el mantenimiento y el ámbito global provoca colisiones: la skill personal gana frente a una skill de proyecto del mismo nombre. El namespace del plugin permite que ambas convivan. Mantendría el nombre de los cuatro puntos de entrada CEO y prepararía una transición explícita de los alias actuales al migrar las skills Sityos. Evitaría crear un agente por cada skill. La delegación se justifica donde haya permisos distintos, contexto aislado o trabajo independiente. En los agentes, precargar solo las skills obligatorias, porque su contenido se inyecta entero. [Instalación de skills](../../install-sityos-agents.sh:41) · [Skills y resolución de nombres](https://code.claude.com/docs/en/skills#resolve-skills-that-share-a-name) · [Frontmatter de subagentes](https://code.claude.com/docs/en/sub-agents#frontmatter-reference).

Las descripciones actuales de Drupal, frontend, DevOps y contenido abarcan tareas amplias y varios clientes. Extraería referencias de marca y detalles de despliegue del cuerpo principal, e identificaría condiciones de activación concretas en cada descripción. En el plugin CEO, `linear-conventions` y `pr-contract` son conocimiento de apoyo. `ceo-run`, `dispatch` y `live-verify` cambian Linear o Git y deben exigir invocación explícita. Los comandos heredados funcionan, y Claude también puede invocarlos automáticamente si carecen de ese campo. La migración a skills se puede hacer por comando sin cambiar `/ceo-system:<nombre>`. [Comandos y skills en Claude Code](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill).

**Hay tres versiones de CEO en los canales examinados.** El plugin que figura instalado en ámbito de usuario está en `0.2.0`, con `ceo-run`, `live-verify` y `pm-digest`. El checkout `develop` está en `0.3.1` e incorpora `dispatch`. El catálogo de la referencia local `origin/master` indica `0.1.0` y el clon carece de tags locales. La referencia remota mencionada es la que ya estaba disponible en el clon. Instalar desde una rama móvil o inspeccionar solo el checkout deja indeterminada la versión efectiva para el usuario. Publicaría una versión probada con tag, documentaría la rama o referencia de distribución y fijaría por consumidor la referencia revisada del marketplace. Mantendría versión de plugin y versión de catálogo sincronizadas si ambas se conservan. [Manifiesto de publicación](../../plugins/ceo-system/.claude-plugin/plugin.json) · [Catálogo](../../.claude-plugin/marketplace.json) · [Referencias del marketplace](https://code.claude.com/docs/en/plugins/marketplace-reference#marketplace-sources).

El README instala CEO con el ámbito de usuario predeterminado, aunque el hook se ejecuta en todas las sesiones con el plugin habilitado. Para consumidores, propondría `.claude/settings.json` con `extraKnownMarketplaces` y `enabledPlugins`, más el paso `claude plugin install ceo-system@sityos-agents --scope project` una vez por clon. La configuración compartida declara la intención de habilitar el plugin y el paso de instalación lo descarga. Para iterar sobre el checkout, `claude --plugin-dir ./plugins/ceo-system` ofrece un punto de entrada distinto del canal publicado. El ejemplo de GitHub Actions debe usar la forma de terminal `claude plugin install`; el README actual pone el comando interactivo `/plugin` en un bloque Bash. ## 3. La ejecución CEO necesita contratos comprobables

**Prioridad alta. El registro de ejecución escribe directamente en la rama base.** Tres prompts repiten la secuencia de añadir el log, hacer commit, ejecutar `pull --rebase --autostash` y hacer push. Aunque el commit se limite al log, el push puede transportar otros commits locales pendientes. También mezcla el estado del árbol de trabajo con una operación de auditoría, multiplica los casos de fallo y contradice una política de integración por PR. Guardaría un resultado estructurado por ejecución, con ID, versión, repositorio, acciones y errores, como artefacto de CI o registro separado; si se exige persistencia en Git, usaría un PR. El preflight debe respetar `.ceo/PAUSE` y la pausa de Linear antes de ejecutar el verificador. Para un proyecto sin configuración, preferiría un diagnóstico local y una acción de alta explícita. Hoy el subagente CEO intenta crear un issue en `TOM` por defecto. [Ciclo CEO](../../plugins/ceo-system/commands/ceo-run.md:7) · [Dispatch](../../plugins/ceo-system/commands/dispatch.md:42) · [Agente CEO](../../plugins/ceo-system/agents/ceo.md:35).

**Prioridad alta. Dos ejecuciones pueden seleccionar el mismo issue o exceder el límite de PR.** Consultar estado, rama o PR antes de lanzar agentes deja un intervalo donde ambos despachos ven los mismos candidatos y huecos. Parte de los agentes consumidores pasan a `Blocked` un issue que ya no está en `Ready`, con lo que un segundo lanzamiento puede interferir con el primero. Empezaría serializando `dispatch` por proyecto. Después incorporaría una reserva idempotente por issue con estado anterior esperado, identificador de ejecución y reconciliación con rama o PR antes de reintentar. Cuando la plataforma no ofrezca una transición condicional, la exclusión deberá residir en el ejecutor que realiza las escrituras. Un candidato ya reservado o fuera de estado debe quedar intacto. El código determinista debe calcular cupos, validar estados, aplicar reservas y registrar efectos. El modelo conserva planificación, evaluación y redacción. [Selección de candidatos](../../plugins/ceo-system/commands/dispatch.md:16) · [Agente Drupal](../../../AI-Automation/.claude/agents/dev-drupal.md:29).

**Prioridad alta. Los worktrees de AI-Automation comparten servicios de desarrollo.** Los tres consumidores CEO examinados configuran `develop` como destino de los PR y tienen `master` como rama predeterminada en la referencia local de `origin`. Claude crea, por defecto, el worktree desde la rama remota predeterminada. Los agentes de desarrollo compensan esto creando ramas desde `origin/develop`, una decisión duplicada que llega después de provisionar el worktree. Fijaría y comprobaría el SHA de base al arrancar. Claude permite `worktree.baseRef: "head"` cuando el ejecutor parte del HEAD verificado, y la creación explícita de worktrees permite elegir una referencia concreta. En AI-Automation, varios agentes comparten base de datos, archivos y caché, y las comprobaciones en localhost apuntan al checkout principal. Mantendría ejecución serial hasta tener por worktree proyecto Compose, almacenamiento, base de datos y endpoint propios, verificados con una prueba concurrente de dos entornos. [Worktrees en Claude Code](https://code.claude.com/docs/en/worktrees#choose-the-base-branch) · [Entorno y comprobaciones del agente Drupal](../../../AI-Automation/.claude/agents/dev-drupal.md:29).

**Prioridad alta. Los permisos efectivos dependen de herramientas heredadas.** PM y verificador conservan Bash aunque su prompt limite los usos a lectura, y sus listas de exclusión se refieren a nombres de herramientas de un conector Linear concreto. El hook global del plugin examina Bash y herramientas de archivos, usa expresiones regulares y bloquea las llamadas coincidentes si falta `jq`. Sirve como barrera adicional en la sesión, con cobertura distinta de la autorización de MCP y del proveedor. Definiría una lista explícita de herramientas y una identidad con permisos de lectura para PM. Para el verificador, limitaría GitHub y HTTP a lectura, y canalizaría únicamente los comentarios y transiciones permitidos en Linear mediante el ejecutor. Las ramas protegidas y las credenciales de cada proveedor deben aplicar los límites fuera de Claude. En agentes de plugin, Claude ignora `hooks`, `mcpServers` y `permissionMode` del frontmatter. [Agente PM](../../plugins/ceo-system/agents/pm.md:4) · [Verificador](../../plugins/ceo-system/agents/verifier.md:4) · [Hook](../../plugins/ceo-system/hooks/deny-dangerous.sh:12) · [Restricciones de agentes de plugin](https://code.claude.com/docs/en/sub-agents#choose-the-subagent-scope).

Los tres consumidores fijan `default: L0` y `ceiling: L2`. La skill define L0 como propuesta y L2 como integración automática, mientras `dispatch` comprueba el techo y el hook reserva el merge al dueño. Conviene definir qué autorización da pasar a `Ready`, qué nivel efectivo puede ejecutar cada rol y qué transiciones requieren revisión humana. El nivel válido debería resolverse y registrarse antes de lanzar agentes. El esquema de configuración también debe resolver los roles a definiciones cargadas. Hoy varios consumidores referencian `ceo-system:review-code`, `ceo-system:docs` o `ceo-system:content`, ausentes del plugin. AI-Automation incluye `frontend`, fuera del catálogo de roles documentado, y el perfil de investigación de job-finder produce informes con un contrato distinto del que espera el dispatcher. La declaración de una skill en documentación tampoco garantiza que esté instalada o precargada. [Niveles y roles](../../plugins/ceo-system/skills/linear-conventions/SKILL.md:66) · [AI-Automation](../../../AI-Automation/.ceo/config.yml:94) · [finanzas-mcp](../../../finanzas-mcp/.ceo/config.yml:97) · [job-finder](../../../job-finder/.ceo/config.yml:85).

El mismo principio se aplica a los comandos fuera de CEO. `drupal-module` promete Drupal 10 y 11 y usa una API de hooks disponible desde 11.1 salvo que se pida compatibilidad; `content-page` anuncia tres idiomas y condiciona el catalán a petición expresa. La skill frontend prescribe Vite, Tailwind y tokens de marca antiguos, mientras AI-Automation documenta sus tokens `--sao-*`. Los contratos reutilizables deberían apoyarse en las capacidades declaradas por el consumidor, con parámetros para versión de Drupal, idiomas y design tokens. [Comando Drupal](../../project-override/.claude/commands/drupal-module.md:13) · [Comando de contenido](../../project-override/.claude/commands/content-page.md:11) · [Guía frontend de AI-Automation](../../../AI-Automation/AGENTS.md:73).

## 4. Cerrar un issue exige evidencias del entorno correcto

El verificador elige **el run exitoso más antiguo entre los últimos veinte que contienen el commit por ancestro de `headSha`**. Eso prueba que hubo un workflow exitoso que incluía ese commit, pero puede divergir del artefacto que sirve el entorno tras otro deploy o un rollback. AI-Automation ya maneja una referencia de artefacto y un flujo de publicación y despliegue. Usaría la evidencia de versión activa y asociaría artefacto, SHA, entorno y resultados de las comprobaciones. Para finanzas-mcp y job-finder, que usan CI en la rama de entrega y apuntan a repositorios privados, distinguiría modos explícitos `live-http`, `ci-only` y `manual`. Si la comprobación requerida es visual y falta navegador, conservaría el estado pendiente con la prueba exacta que debe hacer el dueño. CEO y verificador usan textos de FAIL diferentes en Markdown; un campo de resultado estable y validable permite escalar ese fallo aunque cambie la presentación. [Algoritmo actual](../../plugins/ceo-system/agents/verifier.md:34) · [Formato FAIL esperado](../../plugins/ceo-system/agents/ceo.md:40) · [Publicación y despliegue de AI-Automation](../../../AI-Automation/.github/workflows/build-release.yml:258) · [Entrega de finanzas-mcp](../../../finanzas-mcp/.ceo/config.yml:27).

## 5. Un piloto puede verificar el contrato antes de extenderlo

El contrato inicial de `.ceo/config.yml` puede ser pequeño. Versionaría el esquema y validaría los identificadores del proyecto y sus estados, la rama base, el modo de verificación, los roles habilitados, sus agentes, los límites y los comandos de calidad que aporta el consumidor. Un diagnóstico de solo lectura debe comprobar que esas referencias se resuelven y que las herramientas necesarias están disponibles antes de ejecutar el primer cambio externo. Los pasos de CI, los comandos locales y las reglas propias del repositorio quedan cerca del código al que aplican.

| Fase | Entrega y criterio de salida |
| --- | --- |
| 1. Publicación fiable | Instrucciones de raíz, instalación optativa por repo, versión explícita, comandos mutantes manuales y preflight de herramientas, configuración, roles y rama. Un clon limpio debe resolver la misma versión y los mismos puntos de entrada. |
| 2. Piloto CEO en AI-Automation | Dispatch serial, registro separado de Git, límites aplicados por el ejecutor y verificación por artefacto activo. En pruebas, pausa, fallo de conector o reintento no producen transiciones duplicadas ni pushes a la rama base. |
| 3. Reutilización | Activar un segundo consumidor con modo CI antes de añadir más perfiles. Demostrar que la adaptación requiere configuración y agentes de proyecto, y que el núcleo CEO se mantiene igual. |
| 4. Paralelismo | Habilitarlo tras confirmar aislamiento de base, Compose y HTTP, y que dos ejecuciones sobre el mismo issue producen como máximo una reserva y un PR. |

**Verificación de esta auditoría.** En Claude 2.1.332 pasaron `claude plugin validate --strict .`, la validación separada del directorio del plugin y la validación de los componentes en `agents/`. La validación del plugin informó sobre icono de catálogo y declaración de hosts sin impedir el resultado. Pasaron `bash -n` y las 44 aserciones de la batería existente del hook. Esas comprobaciones cubren estructura, sintaxis y casos del hook. Las rutas de negocio descritas se revisaron mediante inspección y la reproducción del instalador utilizó un entorno aislado. Los flujos CEO que escriben en Linear o GitHub, las credenciales y la ejecución en repos consumidores quedan pendientes de una prueba de integración. Incorporaría fixtures de estado y base Git junto con evaluaciones de Claude usando MCP simulado. Las fixtures deben incluir expiración o fallo de la reserva, roles ausentes, backport, rollback y selección de artefacto. [Suite actual](../../plugins/ceo-system/tests/deny-dangerous.test.sh) · [Evaluaciones y MCP simulado](https://code.claude.com/docs/en/plugin-evals#mock-mcp-servers).

Esta auditoría entrega el informe y la propuesta de migración. El piloto tiene un criterio de adopción concreto: que un clon limpio pueda declarar su configuración, identificar qué versión carga y demostrar en pruebas el efecto de cada operación antes de habilitarla en el proyecto.
